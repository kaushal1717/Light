# Fleet v0.1.2

Date: 2026-09-28

## What changed

`fleet swarm` gains `--prompt-file <PATH>`: the worker's instructions are read from a file
instead of being pasted inline through `--prompt`. Supported formats are `.txt`, `.md`, and
`.pdf` (extension matched case-insensitively).

```sh
fleet swarm --repo . --task EUME-001 --role builder --agent claude \
  --prompt-file docs/plans/001_StnDailyDispatchCron.md
```

### User-visible behavior

- `.txt` / `.md` are sent to the worker verbatim (must be UTF-8).
- `.pdf` is reduced to its text layer with the pure-Rust `pdf-extract` crate; no external tool
  (poppler, etc.) is required. The parser never runs in the CLI process: see "PDF parsing is
  isolated and bounded" below.
- `--prompt-file` and `--prompt` are mutually exclusive (clap usage error, exit 2 — the same
  code as every other usage error in the CLI).
- The file is read before the repo is touched, so the instructions are resolved from the
  caller's working directory, not from the lane's worktree. An untracked plan file works.
- Refused with exit 7 and a message naming the path, never replaced by `--task`'s text:
  unsupported extension, missing/unreadable file, empty or all-whitespace text, non-UTF-8 text,
  a PDF with no text layer (e.g. a scan), a malformed PDF (parser errors *and* parser panics are
  both caught), a PDF that needs more than 256 MiB of memory or 30 s to parse, a file over
  16 MiB, or text over 256 KiB.
- Every one of those refusals, and every other pre-lane `swarm` failure (`--role`, `--task`,
  `--agent`, `--repo`), writes a `Refusal` ledger receipt before exiting (AGENTS.md rule 8). The
  receipt carries the same typed exit code as the process, plus `failure`, `task`, and
  `prompt_file`.
- The 256 KiB text cap exists because the prompt reaches the worker as one argv entry
  (`crates/builder/src/impl_/spawn/child_command.rs`) and macOS caps argv + environment at
  1 MiB (`ARG_MAX`).

### PDF parsing is isolated and bounded

A PDF under the 16 MiB file limit can declare streams that inflate to gigabytes, and neither
`pdf-extract` nor `lopdf` has a decompression limit. lopdf also inflates xref and object streams
while loading, before any caller hook runs, so a bound inside the parser is not possible. So
`swarm` sends the PDF's bytes to a hidden child, `fleet __pdf-text`, which:

- arms a heap cap (`src/alloc_cap.rs`, the global allocator: a pass-through until armed, then any
  allocation past 256 MiB of net growth fails, and Rust aborts the child);
- refuses text over 256 KiB itself, before writing anything to stdout.

The parent kills the child after 30 s, reads at most 256 KiB + 1 of its stdout and 64 KiB of its
stderr, and maps the result to a typed outcome. Exit 7 is the child's own refusal reason; an
abort after a failed allocation is "needs more than 256 MiB of memory"; a timeout, or any other
signal, is also a refusal. Only a child that could not start at all is an environment fault
(exit 3).

Measured on a 6.8 MB PDF whose one content stream inflates to 1 GiB of spaces (the new test
fixture):

| | Wall time | Peak RSS | Exit | Receipt |
|---|---|---|---|---|
| Before (parser in the CLI process) | 7.31 s | 1.62 GB | 7 ("no extractable text") | none |
| After (isolated child) | 0.36 s | 245 MB | 7 ("needs more than 256 MiB of memory") | `Refusal`, exit 7 |

### Fixed: a prompt starting with `-` never reached the worker

The parent passes the prompt to the `__agent` child as a positional argv entry. clap read a
leading `-` as a flag, so a prompt starting with YAML front matter (`---`) killed the child with
a usage error (exit 2) before it opened fd 3. The lane then ended `EnvironmentFault: agent
exited without an fd-3 result`, with no hint of the cause. This affected inline `--prompt` too,
but nearly every `.md` plan starts with `---`, so `--prompt-file` would hit it constantly. It was
found by running a real plan (`posx-eume-backend/docs/plans/001_StnDailyDispatchCron.md`).
`AgentArgs::task` now sets `allow_hyphen_values`, and the argv shape is unchanged.

## Known limitations

- Files already over the 80-line cap that grew: `args_core.rs` (+5), `swarm_cmd_tests.rs` (+4),
  `dispatch/mod.rs` (+13, module declarations), `cli/src/root.rs` (+3). `swarm_cmd.rs` shrank
  (176 → 152). The over-cap set is unchanged from `main` (119 files).
- The heap cap counts net growth after the child arms it, so the child's startup heap (a few
  MiB) is not counted. The cap and the deadline are constants, not configuration.
- The `__pdf-text` child uses `std::os::unix`, like the rest of the fd-3 lane machinery.
- PDF extraction quality depends on the PDF: multi-column layouts and tables can come out in a
  different reading order. Scanned PDFs are refused, not OCR'd.
- `cargo deny` is not installed on the machine that made this change, so the license policy was
  checked by listing `pdf-extract`'s dependency licenses against `deny.toml` by hand (all were
  on the allowlist; `r-efi` already has an exception), not by running the tool.
