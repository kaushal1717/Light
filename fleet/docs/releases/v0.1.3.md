# Fleet v0.1.3

Date: 2026-09-28

Stacked on v0.1.2 (PR #24, `--prompt-file`). This release makes `fleet swarm --agent claude`
able to finish a lane. Before it, every claude lane failed, for three separate reasons found one
after another by running a real lane.

## What changed

### 1. Claude lanes can log in: `CLAUDE_CODE_OAUTH_TOKEN` is forwarded to claude lanes only

The hermetic env gives each lane a fresh tempdir `HOME` and drops `USER`. The macOS `claude` CLI
needs both the real `HOME` (`~/.claude.json`) and `USER` (Keychain lookup) to find its login,
so every claude lane ended `Not logged in · Please run /login`. Verified by hand:

| Child env | Result |
|---|---|
| `env -i PATH HOME=<tmp>` (what fleet did), with or without `USER` | `Not logged in` |
| `env -i PATH HOME=$HOME` | `Not logged in` |
| `env -i PATH HOME=$HOME USER=$USER` | `ok` |
| `env -i PATH HOME=<tmp> CLAUDE_CODE_OAUTH_TOKEN=<token>` | `ok` |

If the parent has `CLAUDE_CODE_OAUTH_TOKEN` set (minted by `claude setup-token`), fleet now
forwards that one variable to **claude lanes only**, after `HermeticEnv::apply`'s
`env_clear()`. The real `HOME` and `USER` are still never forwarded, and codex/freelane lanes
never receive the token. The token is read only from the parent's environment and is not stored
in `HermeticEnv`, whose `Debug` output could be logged.

**Security trade-off (owner decision).** A claude worker can run tools, so it can read its own
environment, including the token. That is less exposure than handing it the real `HOME`, but
more than before, when nothing of the user's crossed the boundary. Unset the variable and
behavior is exactly as before.

### 2. A prompt starting with `-` reaches the `claude` CLI

The `__agent` child passed the prompt to `claude` as a bare argv entry, so a `---` front-matter
prompt produced `error: unknown option '---…'`. It is now passed after `--`, and `--model` moved
ahead of it. Checked live: `claude -p '---…'` gives the error, `claude -p -- '---…'` gives `ok`.
v0.1.2 fixed the same bug one level up (parent → `__agent`).

The codex arm gets the same `--` (`codex exec -- <prompt>`). codex is not installed on the
machine that made this change, so that arm is **unverified live**.

### 3. Claude workers may write files: `--permission-mode acceptEdits` for `worker_default`

`AgentToolPolicy::worker_default()` (every `swarm` lane) passed claude no permission mode.
Under the hermetic `HOME` there are no user settings, so `claude -p` denied every write
("I don't have permission to write that file"), and the lane ended "worker reported done but
left the worktree unchanged". It now passes `--permission-mode acceptEdits`. Checked live in a
hermetic env: the default mode refused to create a file, `acceptEdits` created it. **That mode
also auto-ran `touch`**, so it covers simple file commands as well as edits. It is not
`bypassPermissions`. Restricted (approved-effect) policies are unchanged.

## Known limitations

- `acceptEdits` auto-approved file edits and `touch` in the live check. Which other shell
  commands it approves in `-p` mode was **not tested**. Don't rely on the worker running the
  repo's tests; fleet's gates do that after the lane.
- Workers are still killed after 300 s (`swarm_cmd.rs`), so large plans need splitting.
- `agent_tool_policy.rs` (already over the 80-line cap) grew by 4 lines.
- The codex `--` change is unverified live (codex not installed).
